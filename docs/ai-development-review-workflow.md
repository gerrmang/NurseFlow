# NurseFlow: Claude 개발 · Codex 검토 흐름

## 역할과 산출물

| 담당 | 작업 | 제출물 |
| --- | --- | --- |
| Claude Opus | 요구사항 해석, 기술 설계, API/DB/권한·배치 규칙의 선택지 검토 | 짧은 설계 기록(ADR), 변경할 OpenAPI 항목, 인수 기준, 위험과 롤백 계획 |
| Claude Sonnet | 합의된 설계를 기능 브랜치에서 구현 | 코드, 필요한 테스트, 문서 변경, 검증 결과, PR 설명 |
| Codex | 리뷰 요청에서는 읽기 전용 검토. 구현·수정 요청에서는 작업 브랜치에서 명시적으로 허용된 범위만 수정하며, 병합하거나 `main`·`dev`에 직접 변경하지 않음 | 재현 가능한 결함 중심의 파일:줄 번호, 영향, 수정안, 검증 근거 |

설계와 구현은 [초기 MVP 범위](mvp-scope.md), [API 계약](openapi.yaml), [Git 흐름](runbooks/git-flow.md)을 공통 기준으로 삼는다. 모델 이름은 개발 도구의 역할을 뜻하며, **근무표 자동 생성의 필수 규칙 판단은 서버 검증기**가 맡는다.

## 기능 단위 작업 순서

1. `dev`의 최신 상태에서 `feat/...` 브랜치를 만든다. Opus가 이 기능의 API·DB·권한·예외 상황과 인수 기준을 먼저 명시한다.
2. Sonnet이 해당 브랜치의 변경 범위만 구현한다. Android, 웹, 백엔드가 함께 바뀌면 OpenAPI와 각각의 응답 모델을 같은 기능 단위로 맞춘다.
3. 구현자는 빌드·필수 규칙/권한 테스트를 실행하고 실제 결과와 실행하지 못한 검증을 PR에 적는다.
4. Codex가 변경된 diff와 관련 호출 경로를 검토하고 한글로 보고한다. 지적된 P1/P2는 `dev` 병합 전에 수정하고 다시 검토한다. P3도 실행 오류 가능성이 있으면 병합 전에 수정한다.
5. 기능 PR을 `dev`로 병합한다. 배포할 때 검증된 `dev`를 PR로 `main`에 반영한다.

같은 폴더를 두 에이전트가 동시에 수정하지 않는다. 독립 작업은 별도 worktree/브랜치에서 진행하며, API 계약을 바꿀 때는 소비자(Android·웹)와 백엔드를 함께 확인한다.

## 공유 작업 환경과 인계

- Claude와 Codex는 같은 저장소 worktree와 task branch를 기본 작업 공간으로 사용한다. 한 에이전트가 끝나면 다른 에이전트는 새 checkout을 만들지 않고 현재 브랜치의 변경과 `docs/work-status.md`를 확인해 이어간다.
- 같은 worktree에서는 동시에 파일을 수정하지 않는다. 독립 병렬 작업만 별도 worktree와 명시된 파일 소유 범위로 나눈다. 병렬 변경은 통합한 뒤 공유 worktree에서 검증한다.
- 진행·리뷰 지점은 두 에이전트가 함께 읽고 갱신하는 `docs/work-status.md`에 기록한다. 저장소 밖 또는 `.codex/` 같은 도구별 개인 상태를 유일한 작업 기준으로 삼지 않는다.
- 실제 CI 명령은 `.github/workflows/verify.yml`, 기능별 추가 로컬·기기 검사는 `docs/feature-breakdown.md`를 따른다. 양쪽 모두 실행한 명령과 결과를 그대로 기록하고, 실행하지 않은 검사를 통과로 표시하지 않는다.

## Codex 리뷰 분류

이 표의 **P1~P5는 리뷰 우선순위**이며 [프로젝트 계획](project-plan.md)의 개발 단계 P0~P5와 다르다.

| 분류 | 검토 기준 | 처리 |
| --- | --- | --- |
| P1 | 실제 영향이 치명적이거나 광범위함. 예: 권한 우회, 초안·부재 사유·개인정보 노출, 필수 근무 규칙 위반, 데이터 손실·잘못된 공개, 핵심 흐름 중단 | 병합 전 수정 필수. 재현 조건과 정확한 경로 제시 |
| P2 | 실제 영향이 큼. 예: 기존 기능 회귀, 동시 편집·월 경계 오류, 잘못된 결과·상태 전이, 보안 통제 누락, 핵심 경로의 테스트 공백 | 병합 전 수정 필수. 영향 범위를 명시 |
| P3 | 실제 영향이 제한적이거나 우회 가능하지만 기능·운영에 명확한 불편이나 오류를 일으킴 | 수정 권장. 실행 오류 가능성이 있으면 병합 전 수정 |
| P4 | 영향이 작고 범위가 제한된 결함 또는 품질 저하 | 수정 제안. 필요하면 후속 작업으로 기록 |
| P5 | 실제 영향이 매우 낮은 사소한 불일치나 개선점 | 선택적 개선으로 기록 |

우선순위 P1~P5는 결함의 **실제 영향도(심각도)**로 결정한다. 결함 종류는 별도 태그로 `보안/권한`, `데이터`, `회귀`, `런타임`, `테스트`, `문서` 등으로 함께 보고한다. 테스트나 문서 결함도 실제 영향이 크면 P1/P2가 될 수 있다. P1~P5는 [프로젝트 계획](project-plan.md)의 개발 단계 P0~P5와 다르다.

리뷰는 스타일 선호보다 동작·보안·데이터 일관성을 우선한다. 추정만으로 결함이라고 단정하지 않고, 확인된 사실과 아직 검증하지 못한 위험을 구분한다. 같은 미수정 지적을 매번 반복하지 않는다.

## 수정·재리뷰 원칙 (2026-11-10 추가)

PR #37에서 리뷰 지적을 고친 커밋이 새 경합을 만들고, 같은 패턴의 다른 경로를 빠뜨려 다음 리뷰에서 P2로 다시 발견됐다. 같은 일이 반복되지 않도록 아래를 지킨다.

- **수정 커밋도 다시 리뷰한다.** 특히 잠금·트랜잭션·성능 최적화·권한 판정을 바꾼 수정은 병합 전에 해당 diff를 다시 리뷰받는다. `work-status.md`에 "재리뷰 전"으로 남긴 채 병합하지 않는다.
- **같은 패턴을 함께 찾는다.** 결함 하나를 고치면 같은 구조(예: 잠금 밖에서 읽고 판단한 뒤 쓰기, 이전 값을 읽어 이력 기록)를 저장소에서 검색해 같은 PR에서 함께 고치거나, 고치지 않는 이유를 PR에 적는다.
- **동시성 점검 항목을 리뷰 요청에 고정한다.**
  - 읽기·판단·쓰기가 같은 잠금(병동 행·대상 행) 안에 있는가.
  - 잠금을 잡을지 여부를 잠금 밖에서 읽은 값으로 정하지 않는가.
  - 이력·감사 기록의 이전 값이 잠금 안에서 읽은 실제 직전 상태인가.
  - 잠금 순서가 다른 경로와 같아 교착이 생기지 않는가(현재: 병동 → 계정 → 대상 행).
- **경합 테스트는 순서를 강제한다.** 스레드를 한꺼번에 띄우는 방식은 경합 구간을 매번 만들지 못한다. 테스트 전용 하위 클래스로 첫 요청이 잠금을 쥔 채 멈추고 두 번째 요청이 원하는 지점에 도착한 뒤 풀어 주며, 보호 코드를 되돌린 변이에서 실패하는지 확인해 PR에 적는다.

## 정기 점검 절차 (자동화 설정 시 30분 주기)

- 이 절차는 30분 주기의 리뷰 자동화가 실제로 설정되어 작동하는 환경에서 적용한다. 자동화가 확인되지 않은 환경에서는 예약 실행 중이라고 표현하지 않는다.
- 실행 시 저장소와 `git worktree list`에 나오는 NurseFlow 작업용 worktree의 새 커밋·미커밋 diff를 각각 마지막 리뷰 지점과 비교한다. 변경이 없으면 알림을 보내지 않는다.
- 새 변경이 있으면 변경 파일과 연관 코드·[MVP 범위](mvp-scope.md)·[API 계약](openapi.yaml)을 살펴보고 실제 영향도에 따른 P1~P5 중 **조치 가능한 발견 사항**을 보고한다.
- 정기 점검은 읽기 전용이다. 코드를 수정·커밋·푸시하거나 PR을 병합하지 않는다. 구현자가 수정하면 다음 점검에서 다시 검토한다.
- 자동 점검은 조기 발견용이다. 병합 직전에는 변경 전체에 대한 별도 리뷰와 CI 검증을 실행한다.
- 가상 데이터만 모델과 시연에 사용한다. 실제 간호사 정보, 카카오 토큰, 환경변수·비밀키를 프롬프트나 리뷰 결과에 넣지 않는다.

마지막 리뷰 지점은 공유 worktree별로 경로, 브랜치, 리뷰한 `HEAD` 커밋 SHA, 미커밋 diff 해시(예: `git diff HEAD | shasum`), 리뷰 시각과 검토 주체를 `docs/work-status.md`의 리뷰 지점 기록에 남긴다. Claude와 Codex는 검토를 시작할 때 이 값을 읽고, 완료 후 새 기준점으로 갱신한다.
